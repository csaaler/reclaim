# Cutting a release

Reclaim is distributed as source only for now. A release is a `vX.Y.Z` tag on `main` plus a GitHub release with notes; there are no downloadable app builds, because the app is not signed with a Developer ID or notarized. Users build it themselves with `scripts/build-app.sh`.

This page is for the maintainer.

## How versions work

- [Semantic Versioning](https://semver.org): `MAJOR.MINOR.PATCH`. While the version is below 1.0, a minor bump may contain breaking changes.
  - New features or app support: minor (`0.1.0` → `0.2.0`).
  - Fixes only: patch (`0.1.0` → `0.1.1`).
- **The git tag is the only place the version lives.** Nothing in the repository is edited for a release, and no version-bump pull request is needed.
- `scripts/build-app.sh` writes the version into the built app: `CFBundleShortVersionString` is the latest `vX.Y.Z` tag reachable from the commit, `CFBundleVersion` is the number of commits (it only goes up on `main`). A build between two releases reports the last released version with a higher build number.
- Without git history (a source zip, or a shallow clone without tags) the app keeps the placeholders from `Sources/ReclaimApp/Resources/Info.plist`: version `0.0.0`, build `0`. Do not edit those values.
- Release notes are generated by GitHub from the titles of the pull requests merged since the previous tag, grouped by label as configured in `.github/release.yml` (`enhancement`, `bug`, `documentation`, everything else). `CHANGELOG.md` covers 0.1.0 only and is no longer updated.

## What contributors do

Nothing release-specific. Pull requests are squash-merged, and the pull request title becomes the commit message on `main` and the line in the release notes, so it must describe the change for a user (see CONTRIBUTING.md, "Commits and pull requests"). The maintainer adds the `enhancement`, `bug` or `documentation` label before merging so the change lands in the right section of the notes.

## Steps

1. **Start from a clean, up-to-date `main`.**

   ```sh
   git switch main
   git pull --ff-only
   git status            # must be clean
   ```

2. **Check that CI is green on that commit**, then run the same checks locally:

   ```sh
   swift build
   swift test
   scripts/check-templates.sh
   scripts/check-plugin-rules.sh
   scripts/check-privacy.sh
   ```

3. **Smoke-test the app.** Build a release build and open it:

   ```sh
   scripts/build-app.sh release
   open build/Reclaim.app
   ```

   Run a scan, add a few 🟢 items to the cleanup list and open the review screen. Do not confirm cleanups you do not want on your own machine.

4. **Pick the version** from the changes since the last tag:

   ```sh
   git describe --tags --abbrev=0                       # last release
   git log --oneline "$(git describe --tags --abbrev=0)"..HEAD
   ```

5. **Create the release.** This tags the current `main` commit on GitHub and writes the notes:

   ```sh
   gh release create vX.Y.Z --target main --title "Reclaim X.Y.Z" --generate-notes
   git fetch --tags
   ```

   Then edit the release on GitHub (or use `--notes-file` instead of `--generate-notes`) and add at the top:
   - the Xcode and Swift version you tested with, and the macOS version;
   - "Source only. Build with `scripts/build-app.sh`. The app is ad-hoc or development signed and not notarized.";
   - a link to the README's safety section.

   Do not attach app bundles or zips while releases are not notarized.

6. **Check the result:** the release page lists the right pull requests, and `scripts/build-app.sh release` on a fresh clone shows the new version in Reclaim > About Reclaim.

### The first release, 0.1.0

There is no earlier tag, so generated notes would list every pull request. Use the 0.1.0 section of `CHANGELOG.md` as the notes instead:

```sh
gh release create v0.1.0 --target main --title "Reclaim 0.1.0" --notes-file <(sed -n '/^## \[0.1.0\]/,/^\[0.1.0\]:/p' CHANGELOG.md | sed '1d;$d')
```

### Fixing a mistake

A release tagged on the wrong commit or with the wrong number can be removed and created again, as long as nobody has relied on it yet:

```sh
gh release delete vX.Y.Z --cleanup-tag --yes
git tag -d vX.Y.Z
```

Once a version has been public for a while, do not reuse its number; release the next patch version instead.

## Security fixes

Fix privately reported problems in a temporary private fork (GitHub creates one from the security advisory), merge the fix to `main`, release a patch version, then publish the advisory. Credit the reporter in the advisory and the release notes if they want it. The app has no auto-update, so the release notes must say clearly that users need to pull and rebuild.

## Later: binary releases

Shipping a downloadable app needs a Developer ID certificate (Apple Developer Program), a hardened runtime, notarization with `notarytool` and stapling. That would also keep Full Disk Access across updates. Build such releases only from a reviewed tag on `main`, on the maintainer's machine or in a workflow that runs only on tag pushes with a protected environment, never from pull request workflows. Publish SHA-256 checksums with every artifact. Update this page, the README and SECURITY.md when that happens.
